BLOCKER CORRECTNESS · Nil deref on refund path · internal/refund/service.go:134-137 · implementation · codex

Issue

refund.Account is only populated for card payments; for wallet refunds it stays nil and acct.Balance panics, taking down the whole refund worker.

acct := r.accounts.Find(refund.AccountID)
// acct may be nil for wallet refunds
acct.Balance += refund.AmountCents // panics

Suggested fix

Guard the lookup and fail the single refund instead of the worker:

acct := r.accounts.Find(refund.AccountID)
if acct == nil {
    return fmt.Errorf("refund %s: account %s not found", refund.ID, refund.AccountID)
}
acct.Balance += refund.AmountCents

Why it matters / details

  • It crashes the whole refund worker, so no refunds go out until someone restarts it.
  • ELI5: For wallet refunds the account object is empty, and the code reads a field off the empty thing.
CRITICAL CONTRACT · Unversioned breaking API change · api/v1/payments.proto:52 · architecture · opus

Issue

amount (int64) was renamed to amount_cents on the existing v1 message. Deployed clients still send amount, which now silently decodes to 0 — every charge becomes free.

  // was: int64 amount = 3;
  int64 amount_cents = 3;

Suggested fix

Introduce the field as v2 or add amount_cents alongside a deprecated amount, and migrate consumers before removing it. Never repurpose a tag on a shipped message.

Why it matters / details

  • Old clients keep sending the old name, it reads as 0, and every charge becomes free.
  • ELI5: A field that clients already send was renamed without bumping the version.
HIGH CONCURRENCY · Race on shared ledger map · internal/ledger/cache.go:88 · implementation · codex

Issue

entries is read in Get and written in Apply from multiple goroutines with no lock — go test -race flags it and balances can corrupt under load.

func (c *Cache) Apply(e Entry) {
	c.entries[e.Account] = c.entries[e.Account] + e.Delta
}

Suggested fix

Protect with a sync.RWMutex (RLock in Get, Lock in Apply), or switch to sync.Map if the access pattern is write-light.

Why it matters / details

  • Under load the balances can corrupt and the race detector fails the build.
  • ELI5: Two goroutines touch the same map at once without a lock.

HIGH SECRET_EXPOSURE · Hardcoded provider API token · config/providers.go:17 · security · opus

Issue

A live Stripe-style secret is committed in source. Anyone with repo read access can move money; it also leaks into build logs and images.

const providerToken = "sk_live_4eC39HqLyjWDarjtT1zdp7dc"

Suggested fix

Load it from the secret manager at runtime and rotate the exposed token immediately:

token := secrets.MustGet(ctx, "payments/provider_token")

Why it matters / details

  • Anyone who can read the repo can spend money, and it leaks into logs and images.
  • ELI5: A real payment secret is written straight into the code.
MEDIUM ERROR_HANDLING · Webhook error swallowed · internal/webhook/handler.go:76 · implementation · codex

Issue

The error from process(evt) is assigned to _, so a failed webhook returns 200 and the provider never retries — events are lost silently.

_ = process(evt)
w.WriteHeader(http.StatusOK)

Suggested fix

Return a 5xx on failure so the provider redelivers, and log with the event id.

Why it matters / details

  • The provider thinks it succeeded and never retries, so events vanish.
  • ELI5: If handling a webhook fails, the code still says 'OK'.
MEDIUM PERFORMANCE · N+1 query in invoice list · internal/invoice/list.go:44-49 · maintainability · gpt

Issue

For each invoice the handler issues a separate LoadLineItems query — a 200-invoice page fires 201 queries and dominates p99 latency.

for _, inv := range invoices {
	inv.Items, _ = db.LoadLineItems(ctx, inv.ID)
}

Suggested fix

Batch with a single WHERE invoice_id IN (...) and group in memory, or use a join.

Why it matters / details

  • A big page fires hundreds of queries and gets slow.
  • ELI5: It runs one extra database query per invoice in the list.
